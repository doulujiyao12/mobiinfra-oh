# 个人记忆增量同步

同步仍以原始日志、图库分析结果、聊天同步记录和已授权的日历为事实来源。邮件单独读取并保留今天及前两天的内容，首页只展示今日关注项，不进入个人画像。用户同意数据处理并开启对应来源后，跨天首次打开应用会自动更新邮件、日历和新增聊天；开屏自动更新不导入图库或任务记录。自动更新只检查聊天整理文件和日历快照的变化，未变化时不构建索引，也不更新全量手动同步快照。

任务页“一键执行”在整批采集结果保存后，另行触发一次完整的增量记忆分析，更新画像、采集分组和提醒，支持手机自控、电脑控制和通知触发。此次同步不重新读取邮件或日历；已有同步尚未结束时，等待完成后再检查新采集的数据。主动停止采集时不启动分析；任务部分失败仍同步已保存结果，同步失败保留采集文件并提示重试。图库分析结果也仍可通过汇总页手动同步。

自动更新的进度弹窗可直接关闭“每日自动更新”，也可到“我的 → 数据采集 → 每日自动更新”调整。关闭会持久保存，不影响手动同步；当前已开始的来源处理完成后，后续来源不再启动。日历未授权、邮箱未开启或缺少完整账号配置/授权码时会跳过，不弹授权窗口、不连接未配置的邮箱，也不计为同步失败。未授权日历的旧缓存保留在本机，但不再展示或发送给模型分析。

开屏不会主动弹出隐私声明。尚未同意当前声明时会静默跳过自动分析，用户主动使用需授权的功能或进入隐私设置时仍可确认。日历和聊天同时需要更新时，先读取日历，再统一整理聊天及更新一次记忆索引，避免连续构建两次画像。已完成的来源会提前跳过，不重复读取邮箱授权码。

## 更新机制

- **画像**：按领域、年代、年份、季度和月份构建摘要树；大月份再按事件标识的哈希稳定分块。新增或修改事件只更新相关分块和上层摘要，不移动后面的历史分块。单次分块限制事件数和大小，摘要合并也有请求长度与轮数限制。
- **事实依据**：分块允许保存单条观察，以便跨月份形成线索；最终画像继续要求多条有效证据。事件原文和检索索引独立保留，摘要不替代原始事实。日历明确标为安排，不能作为已经完成的行为。个人信息场景仍排除在自动画像之外。
- **缓存失效**：事件内容、日期、来源、日历元数据、模型 URL、模型名、处理策略或提示词变化会使相关缓存失效。单独更换 API Key 不重算历史，也不会将 API Key 保存进缓存。父摘要只使用本轮有效子摘要，不反复叠加旧画像，因此已移除的证据不会通过旧画像继续传播。
- **日志修改和删除**：已经合并的事实不能精确减去某条输入，故仅重建受影响的“月份＋来源文件”组。当前整理产物清单是权威来源；已移除来源遗留的旧产物不再被索引目录扫描重新收录。已知且实际存在的日志可通过历史快照补足目录枚举，读取失败会报错，避免误判删除。
- **事件分析**：成功的模型分类保存独立检查点；后续画像失败后重试，可直接复用这部分结果。启发式回退不会写为成功的模型检查点。
- **索引**：按变化事件修改关键词、来源、领域和场景倒排表；事件与时间分区只写受影响月份，并清理已移除的月份。实体部分沿用已有增量归并逻辑。待办等小型文档仍按当前事件生成，内容未变化时跳过写入。
- **共享读取**：一次同步及一次首页/汇总展示刷新分别共享事件快照，文件文本缓存限制在索引目录内、最多16 MiB；写入时失效，阶段结束后释放。

## 失败与恢复

模型成功的分块和事件检查点位于应用沙箱中的 `workflows/profile-consolidation/sync-cache/`。每个节点保存输入和输出校验信息；模型失败或检查点损坏不会被当作成功缓存。

索引先在私有覆盖层构建，完成后将有变化的文件暂存至 `workflows/profile-consolidation/indexes.pending-sync/`，再写入 `prepared.json`。发布是同步操作；若发布阶段进程中断，下次读取索引前校验并重放完整恢复记录。恢复文件缺失或损坏时停止读取并报告错误，不把混合版本当作正常结果。模型阶段失败不会改写已发布索引。

这些检查点只恢复数据处理，不会自动下发或重放手机 GUI 操作。用户仍需点击同步重试。

## 进度与 Debug

画像阶段显示已完成的摘要节点数、复用数和更新数；采集分组显示场景完成数量。其他阶段显示处理状态，避免把固定的99%误认为只剩1%的工作量。

开屏自动更新会显示当前阶段、实际处理计数、已处理来源数量、阶段进度条和已用秒数。连接邮箱、读取标题/正文、AI筛选、日历日期分段/详情、聊天及画像处理均回传进度；等待期间保留加载动画。进度代表处理阶段和计数，不是剩余耗时估计，也不会随计时器虚增。

打开“我的”中的 Debug 开关后，可按以下关键词定位日志；关闭时沿用统一日志开关，不额外保存诊断日志：

| 日志 | 含义 |
| --- | --- |
| `SYNC_STAGE_BEGIN` / `SYNC_STAGE_END` | 阶段名称和实际墙钟耗时 |
| `SYNC_MODEL` | 个人记忆流水线的实际模型请求数、累计请求等待毫秒、输入字符数；不是 token 用量 |
| `SYNC_PROFILE` | 摘要节点复用、更新以及调用模型的节点数；一个节点可能发出多个预算受限的请求 |
| `SYNC_ENRICH` | 待分类事件数和检查点命中数 |
| `SYNC_EVENT_DELTA` | 当前事件量和变化事件量 |
| `SYNC_INDEX_WRITE` | 实际写入和复用的文件数量 |
| `SYNC_READ_CACHE` / `PRESENTATION_READ` | 同步、展示刷新读取缓存的情况 |
| `SYNC_FINISH` | 本轮成功状态和总耗时 |

外层日历、今日邮件和个人记忆各有阶段计时。模型请求的累计等待可能包含并发等待，不能直接等同于同步总耗时。新增诊断只包含阶段、耗时和数量；画像 JSON 解析失败也不再输出原始回复。

自动更新另记录 `STARTUP_SYNC_READY`（授权和邮箱配置检查耗时）、`STARTUP_SYNC_BEGIN` 及每个来源完成时的 `elapsedMs`；邮件还记录 `MAIL_READ_DONE` 和 `MAIL_ANALYSIS_BATCH`。这些信息可区分读取邮件、AI等待与记忆处理的实际耗时，不包含邮件正文、账号或凭据。

## 首次使用与实际边界

首次运行新版本需要迁移处理标记并建立历史摘要缓存，仍可能较久。缓存建立后，同样的少量新增数据主要触发相关分块的模型工作。原始日志扫描、内容哈希、部分全局 JSON 索引的序列化及展示仍会受历史总量影响，不能承诺同步时间完全独立于历史数据量。

已有几个月历史数据时，无需清空索引或重新采集。原始日志、图片和聊天记录不会因本次升级被删除。旧快照没有新的流水线标记，首次手动同步会重新检查历史来源；旧事件分类清单若缺少当前模型名，也会重新分类相关历史记录。画像输入哈希使用了新策略，相关历史画像会重新生成并建立分块缓存，因此旧派生索引和画像并非完全不变。新索引在构建成功后发布，模型阶段失败仍保留已发布索引；后续相同输入和配置可复用缓存。

模拟基准在240条、2400条历史事件的同一已有月份追加1条事件，两组均只重新分析1个原始数据分块、合并4个摘要节点。这验证模型工作量的复用机制，不代表真机耗时或真实模型回答质量已经完成验证。

## 验证

`scripts/check_incremental_sync.cjs <typescript-module-path>` 执行生产业务逻辑的模拟测试：缓存、模型变更、历史编辑/删除、稀疏月份、输入预算、失败重试、发布恢复、目录枚举失败、读取缓存，以及差量索引和完整重建的随机对照。

`scripts/check_task_batch_sync.cjs <typescript-module-path>` 验证任务批量执行后的自动同步，包括两种控制方式、通知入口、停止、部分失败、并发锁、失败重试及权限变化。

这次没有执行 Hvigor 构建、签名、安装、真机同步或实际用户数据的模型请求。后续用 DevEco 安装后，可在 Debug 下比较同量新增数据的阶段耗时，并核对生成画像的语义质量。
